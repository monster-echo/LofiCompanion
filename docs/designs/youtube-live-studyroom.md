## Problem Statement

LofiCompanion 已上架双商店（v1.0.7）并有 IAP/皮肤收入功能，但缺少一条内容型获客渠道。把 app 已有的自习室房间视觉（MiniMax H3 生成循环视频）+ 同源 lofi 音乐，合成 7×24 可推流的内容，运营 YouTube 直播频道（lofi girl 模式），把观众转化为可归因的 app 下载。

用户原话锚定：「选择其中一个（study room）推流到 youtube」；修正案：「做横屏，app 不内嵌，app 里面的弹幕，以后会在推流上面展示。」

## Demand Evidence

- 品类先例：24/7 lofi 直播是被验证十年的内容形态（lofi girl 千万订阅），品类需求无需再证明。
- 自有前提：音乐全自产/AI 生成，版权链条干净（用户确认）——Content ID 认领风险解除。注意：2025-07「inauthentic content」政策是 YPP **变现**门槛，不影响开播——**一期变现=N/A（YPP 明确不在范围内）**；纯循环流恰是 YPP 拒绝的形态，若未来以变现为目标，内容需向场景/状态轮播演进（方案 B 播放列表原生支持）。
- 诚实缺口：无自有渠道数据。验证期的意义就是补上这块：留存曲线、外链点击、可归因下载。

## Status Quo

目标听众（学习/工作需要背景音的人）现在听 lofi girl 等既有频道或各自的音乐 App。我们在该场景中不存在。自己动手做这个渠道的替代方案（本机 OBS 手动推流）不可持续——Mac 合盖即断流。

## Target User & Narrowest Wedge

- 目标观众：YouTube 上搜 lofi / study with me / ambient 的人群，与 app 目标用户高度重叠。
- 最窄楔子：**单房间定时直播验证版**——横版房间循环视频 + 歌单合成，跑 3-5 场定时直播，看留存与外链点击，数据决定是否升级 24/7 自动基建。不做多房间轮播、不做 app 内嵌、不接弹幕（均为二期候选）。

## Constraints

- 现有房间循环视频为竖版 2K 无音轨（`tools/video-gen`，1290×2796）——横屏是已拍板决策，需出横版海报重跑生成管线（MiniMax H3 宽高比自适应首帧）。
- 音乐与视觉全自产，可安全通过 Content ID；歌单构建需先盘点曲目库总量与授权记录。
- 第一期零 RN app 改动；导流靠频道简介/置顶评论/直播标题的 UTM 链接。
- YouTube 开播前置：频道手机验证 + 约 24h 激活延迟；encoder 推流无订阅数门槛。

## Premises

1. 内容 = 选定房间的循环视觉 + app 同源 lofi 音乐的合成流；**横屏**产出（用户拍板，重跑生成管线出横版）。
2. 第一期零 app 改动：只做服务器侧合成/推流工具链 + YouTube 频道运营 + **归因落地页**（归因链路的一部分，非 app 改动）；**app 不内嵌直播**。
3. **弹幕上屏是规划需求**（用户原话确认）：app 内房间弹幕（biz-server roomHub SSE）未来叠加到推流画面——架构必须给 overlay 留位，不兑现则以静态 overlay 页占位。
4. 验证路径 = 定时直播（单房间、3-5 场）→ 数据决定是否升级 24/7 自动基建，不跳过验证。
5. 成功指标 = 90 天可归因增量，**分平台定义**（iOS 商店链接不吃 UTM → 以落地页点击为准；Android 叠加 Play install referrer 记安装为准），渠道 go/no-go 唯一数字；订阅/观看时长为过程指标。归因落点=轻量落地页（本期一并建，Open Question 6 已决）。

## Approaches Considered

### Approach A: 预渲染循环裸推
横版循环+歌单预混成 1-2h MP4，`ffmpeg -stream_loop -1` 裸推 RTMPS，docker 保活。
Effort S（human 2-4 天 / CC〔Claude Code〕半天），Risk 低。最少运动部件，但预渲染文件无法叠实时弹幕——弹幕需求兑现日即重架构日。

### Approach B: 无头 OBS 播控容器（选定）
Docker 跑无头 OBS：媒体源播横版循环视频列表 + 音乐歌单，浏览器源挂本地 overlay 页（预留），内置 ffmpeg 推 RTMPS；**只跑 ora1**（境外机房——RTMPS 到 YouTube 需境外可达，tengxun-2 境内直推 Google 不可行），复用 ghcr CI 镜像发布。同一 stream key 可从任意外部机器应急重推，这是真实的故障转移故事。
Effort M（human 5-8 天 / CC〔Claude Code〕1-2 天），Risk 中低。**Day-1 spike（已按 2026-09-11 ora-sg-01 实测收窄）**：目标机为 aarch64——arm64 上带 obs-browser（CEF）的 obs-studio 镜像稀缺，故**一期编码引擎定为 ffmpeg**（合成+静态 overlay 用 drawtext/PNG，2 vCPU 可靠）；**B 的架构价值全部保留**：同一播控容器（播放列表/场景/overlay 槽位/restart 保活），二期弹幕上屏时再选 overlay 渲染器（arm64 自编 OBS+CEF / headless Chromium 画面串流进 ffmpeg / 异机 amd64 合成节点）。
✅ overlay 槽位原生预留：弹幕页接现有 roomHub **SSE**（roomHub.ts 为 SSE 实现，浏览器源里 EventSource 天然合适），零重架构；播放列表/场景切换内置，多房间轮播与 24/7 升级同容器完成。
⚠️ 二期弹幕上屏注意：roomHub 访客连接计入在线人数——overlay 客户端须以不进 presence 统计的服务身份连接，否则 app 内在线数永久虚高；token 过期会断认证流，长连需续期策略。

### Approach C: 第三方 SaaS 代推（Upstream/LiveReacting 等）
上传成片+歌单，SaaS 代推。Effort XS，但月费+内容出域+无 overlay 路径，核心增长资产受制于第三方。

## Recommended Approach

**B：无头 OBS 播控容器。** 决定性理由是用户亲口确认的弹幕上屏需求：A 的成片是死的，C 没有自建 overlay 路径；只有 B 的 overlay 浏览器源能在弹幕兑现时接上现成 roomHub SSE 而不停播重架构。同一容器就是未来 24/7 基建本体，验证到常驻零换血。A 保留为 B 调试受挫时的降级路径（合成管线两家共用）。

## Stream Spec 与运维

- **输出规格**：1080p30 起步（x264 veryfast，视频 4-6 Mbps，音频 AAC 256k）；目标机仅 2 vCPU ARM 且与生产容器共享——首场压测若掉帧，降至 720p30 不影响验证结论。
- **视觉源**：横版 2K 房间循环（生成管线仅支持 768P/2K）降采样到 1080p；首发推 `focusing` 态循环。
- **音频管线**：mp3 歌单池顺序/随机播放，响度归一（loudnorm ≈ -16 LUFS），曲间交叉淡化；曲目授权记录随池归档。
- **保活与监控**：docker `restart=always` + 看门狗（obs-websocket 心跳或 YouTube Data API 轮询 stream status），异常告警 + 中断自动重推——直播中途静默卡死等于毁掉那一场的验证数据。ora1 当前无现成告警通道：**告警接线列为 Day-1 任务**（看门狗脚本 → Telegram bot/webhook/邮件，形式当场定，但必须有出口）。
- **媒体分发**：成片与 mp3 池放 **Cloudflare R2**（境外存储已落地），容器按需拉流+本地小缓存（≤1 文件）——ora-sg-01 磁盘仅 540M 余量，媒体不入本地盘；镜像只含程序不含媒体。
- **前置清理（开播硬门槛）**：ora-sg-01 磁盘 99% 满必须先清（docker 镜像/卷清理或挂 Block Volume）——99% 满盘同时威胁 lofi-biz/zhongbei-auth 生产容器，这条与直播无关也要做。
- **占位 overlay 版式（一期就定死）**：台标 + 正在播放 + 时钟——这个布局就是二期弹幕层继承的版式，现在定义清楚，二期「弹幕上屏」是字面意义的换页。

## Open Questions

1. **首发房间选哪个？**（建议视觉动线最强的房间；三个候选：rainy-study-room / midnight-workstation / sunny-classroom）
2. **横版海报出图方式**：现有 poster 是竖版 1290×2796，需新出 16:9 横版首帧（codex imagegen / jimeng 均可），再进 MiniMax H3 生成。
3. **音乐资产盘点**：曲目总数、总时长、授权记录归档；歌单构建工具（mp3 池 + 顺序/随机序列）尚未存在，需小工具。
4. ~~推流机落位~~ **已决：ora-sg-01（新加坡）**。实测（2026-09-11 ssh）：aarch64（Ampere ARM）/ 2 vCPU / 11GB RAM / 负载 0.22 / 磁盘 99% 满（45G 剩 540M）。两个后果进 Stream Spec 与 Dependencies：编码按 1080p30 veryfast 起步、掉帧降 720p；媒体不入本地盘，走 R2；**开直播前先清理磁盘**（99% 满盘同时威胁 lofi-biz/zhongbei-auth 生产容器）。tengxun-2 境内直推 Google 不可行，维持排除。
5. **YouTube 频道现状**：新建品牌频道还是已有频道？新建需手机验证 + 24h 等待。
6. ~~归因链路落点~~ **已决：建轻量落地页**（静态页，埋点+UTM 中转+推广码发放，挂 biz-server 或 CF 页面）。理由：iOS App Store 链接不吃 UTM，只有落地页能同时覆盖双平台可度量归因（iOS 记点击、Android 叠加 Play install referrer 记安装）。
7. 24/7 阶段的直播重建策略：单场直播超 12h 建议重建 broadcast（DVR/归档限制），自动化脚本属二期。

## Success Criteria

- **Go/No-Go（90 天）**：可归因增量 ≥ **300**（预注册阈值：iOS 落地页点击 + Android Play referrer 安装，合并计；仅允许前两场直播后做一次性校准，此后不再动——避免看着数据挪门柱）。
- **验证期（3-5 场内）**：平均观看时长、留存曲线形态、简介外链点击率——三者决定是否投入 24/7 基建。
- 过程指标（不作为决策依据）：订阅数、峰值在线、观看时长总量。

## Distribution Plan

- 频道本身即分发渠道；容器镜像走现有 ghcr CI（monster-echo 命名空间）发布到 ora1，与 lofi-biz 同一套发布纪律。
- YouTube 侧：预约定时直播（YouTube Studio 可排期）、封面、标题带关键词（lofi / study with me）、简介+置顶评论挂**落地页链接（带 UTM）**——不直链商店。
- 推流密钥等凭证：放 ora1 服务器本地环境/secret，不入仓。

## Dependencies

- 横版海报出图 → `tools/video-gen` 重跑横版循环（管线现成，改首帧比例与提示词）。
- 音乐歌单池整理 + 曲目授权记录归档。
- YouTube 品牌频道创建 + 手机验证（24h 激活延迟，决定项目最早开播时刻）。
- 无头 OBS 容器镜像（obs-studio + x264 + 浏览器源依赖）。
- 二期候补：overlay.html + roomHub 弹幕只读客户端；多房间轮播；app 内推广位。

## The Assignment

**本周内：创建/确认 YouTube 品牌频道，完成手机验证，然后在 YouTube Studio 预约第一场 2 小时定时直播（本周日固定档期）。** 开播日期是整个项目的第一颗钉子——预约动作会倒逼横版视频、歌单、容器三件事按期完成。哪怕首场用占位成片，也要让日历上出现那个时间点。

## What I noticed about how you think

- 你没有在我的前提清单上直接盖章。我给的是「全部同意」，你回的是修正案：「做横屏，app 不内嵌，app 里面的弹幕，以后会在推流上面展示。」——三处修正全在往前看（横屏照顾桌面观众、不内嵌守住 app 边界、弹幕上屏把现有产品功能变成直播间卖点），这是产品直觉在推方案，不是在应付提问。
- 你说「选择其中一个推流」，下一个念头就是弹幕上屏——你在把已有资产（房间体系、roomHub 弹幕）当积木反复重组，同一个房间系统，用户侧是自习室，频道侧是直播内容，互动侧是弹幕上屏。资产复用思维是这个仓库一贯的打法（皮肤海报→视频→直播也是同一条链）。
- 从雨夜书房单皮肤到三房间、从 IAP 到订单中心到这条渠道，你每一步都在给下一步铺管线。这条直播链路的每一环（出图→视频生成→合成→推流）都有现成的上一环。
